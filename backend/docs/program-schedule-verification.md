# 지원·평가 기간 검증 결과 (2026-11-05)

## 마감 안내 팝업 및 성공 응답 확인

팝업 뒤에 중복되던 상단 기간 안내·하단 오류 메시지·하단 액션 안내와 첨부 안내는
팝업이 열려 있는 동안 숨긴다. `checkPeriod`의 마감 상태 갱신과 `setError`가
각 표시 영역을 동시에 활성화한 것이 원인이었다. 일반 검증·저장 오류 안내는 유지한다.
브라우저에서 마감 사유가 팝업 한 곳에만 표시되고 확인 후 홈으로 이동하는 것을 재검증했다.

홈 상단 마감 배너는 사용자 피드백으로 제거했다. 마감을 확인하면 원래 화면 위에
"지원 마감 안내" 팝업과 미처리 안내를 표시하고, "확인"을 누른 뒤 홈으로 이동한다.
마감된 요청은 보내지 않으며 서버가 마감으로 거절했을 때도 같은 팝업을 사용한다.

현재 성공 처리 흐름도 확인했다. 서버는 문자열 성공 메시지 대신 HTTP 200과
`ApplicationDetailResponse`(상태·제출/수정 시각·지원 정보)를 반환한다.
`@Transactional` 서비스의 저장 처리가 끝난 뒤 컨트롤러가 응답을 반환하며,
프론트는 `mutateAsync` 완료를 기다린 후 성공 화면을 표시한다.

| 동작 | 현재 성공 안내 |
| --- | --- |
| 지원서 제출·전체 지원서 수정 후 재제출 | 제출 상세로 이동, "제출 완료" 및 "지원서가 정상 접수되었습니다." 표시 |
| 임시저장 | 작성 화면에 "임시저장되었습니다." 표시 |
| 팀·본인 정보 수정 | 편집 모드가 닫히고 갱신된 정보 표시. 별도의 성공 문구는 없음 |

## 마감 확인 후 홈으로 이동

마감 확인 후 입력값을 잠가 두는 동작은 이후 사용자 피드백으로 변경했다.
현재 열린 작성·팀 정보 편집 화면은 시간 경과만으로 이동하지 않는다.
저장·제출·수정·첨부 변경 시 마감을 확인하면 쓰기 요청을 보내지 않고 홈으로 이동한다.
홈에는 "지원 마감 시간이 지났습니다. 제출/수정 요청은 처리되지 않았습니다." 안내를 표시한다.
서버 접수 시각 검사에서 마감으로 거절한 경우에도 같은 안내와 이동을 적용한다.
이번 요청의 변경 내용을 반영하지 않으며 기존 저장·제출 내역은 삭제하지 않는다.

추가 검증: 프론트 35개 테스트, 수정 파일 ESLint, 프로덕션 빌드 통과.
실제 React 페이지에 임시 API 응답을 연결한 브라우저에서 다음을 확인했다.

- 마감 후 제출: 쓰기 요청 0건, 홈으로 이동해 제출 미처리 안내.
- 프론트에서는 기간 내로 보이지만 서버가 마감으로 거절: 제출 요청 1건 거절 후 홈 안내.
- 팀 정보 편집 중 마감 후 저장: 수정 요청을 보내지 않고 홈으로 이동.

## 최종 정책 변경: 클릭 시 검사·서버 접수 시각 판정

아래의 실시간 편집 잠금·파일별 중단 정책은 이후 사용자 피드백으로 대체됐다.
현재 작성·팀 정보 편집 화면은 시간이 지나거나 배경 조회가 발생해도 입력을 잠그지 않는다.
저장·제출·수정·첨부 변경을 누를 때 기간을 검사하고, 만료된 경우에만 화면을 잠근다.

서버는 HTTP 필터 체인 진입 시각을 기록해 지원서·첨부 변경 허용 여부를 판단한다.
접수 후 DB 조회·잠금 대기·저장 중 마감이 지나도 허용 기간에 접수한 요청은 완료한다.
서버 도착 자체가 늦으면 거절하며 브라우저가 보낸 시각으로 우회할 수 없다.

지원자의 여러 파일은 `/api/teams/{teamId}/attachments/batch` 한 요청으로 전송한다.
서버 접수 시각·허용 여부·합산 개수를 검사한 뒤에는 파일 사이에 기간을 다시 검사하지 않는다.
아래의 파일 선택 후 개별 요청 중단 기록은 이전 구현의 검증 기록이다.

최종 자동 검증: 백엔드 87개, 프론트 34개 통과. 프론트 수정 파일 ESLint와 빌드 통과.
백엔드에는 필터 접수 시각 고정·클라이언트 시각 헤더 무시, 마감 이후 처리되는 지원서 저장·제출·수정,
배치 업로드, 배치 권한·최대 개수·첨부 비허용·개별 파일 오류 검사가 포함된다.
브라우저에서는 열린 화면이 마감·재조회 후에도 유지되고, 제출 클릭 때 요청 없이 잠기는 것과
마감 전 시작한 저장·여러 파일 업로드가 지연 응답으로 마감 후 완료되는 것을 확인했다.

## 지원자 화면 수정 후 재검증

아래 최초 검증에서 발견한 지원자 화면의 날짜 비교를 시각 비교로 교체했다.
홈·작성·제출 지원서·내 지원 목록·팀 정보에 공통 기간 판단과 서버 기준 시계를 적용했다.
수정은 지원 시작 포함/마감 제외, 취소는 평가 시작 제외 기준이다.
화면 갱신은 1초 간격이며, API 호출 직전에는 최신 쿼리 캐시와 현재 시각으로 다시 검사한다.

- 전체 프론트 테스트 33개 통과.
- 지원·평가 기간 관련 테스트 21개를 UTC, America/Los_Angeles, Asia/Seoul에서 각각 실행해 모두 통과.
- 수정 파일 ESLint, 프로덕션 빌드 통과. 기존 번들 크기 경고는 남아 있다.
- 실제 React 페이지와 임시 API 응답을 연결한 브라우저 검증:
  - 작성 화면: 시작 시 자동 활성화, 마감 시 잠금, 입력한 이름 보존.
  - 일정 연장·서버 거절 후 재조회 시 작성 내용 보존.
  - 파일 선택창에서 마감 후 선택하면 업로드 요청 0건.
  - 두 파일 순차 업로드 중 마감되면 첫 파일 성공 후 두 번째 파일 미요청 및 중단 안내.
  - 지원 마감 후 제출 지원서의 수정 버튼 잠금, 평가 시작 전 취소 버튼 활성 유지.
  - 취소 확인이 지연되어 평가가 시작되면 취소 요청 차단.
  - 팀 정보 편집 중 마감 시 입력·저장 잠금, 작성 내용 보존.
  - 홈에서 시작 시각에 접수 예정 → 지원 가능 목록 이동.
  - 내 지원 목록에서 평가 시작 시 취소 버튼 자동 잠금.

재현용 API 응답과 파일은 테스트용이며, 브라우저에서 실제 지원서를 수정·취소하지 않았다.
검증 페이지는 삭제했다. 화면 기록은 `backend/build/applicant-period-fixed.png`에 있다.
서버 코드는 이번 지원자 화면 수정에서 변경하지 않았으며,
아래 백엔드 75개 × 3개 시간대 통과 기록은 최초 검증 결과다.

이하 내용은 문제 발견 당시의 기록이며, 지원자 화면 미완료 표시는 위 수정으로 해소됐다.

## 자동 테스트

백엔드 관련 테스트 75개를 각 JVM·PostgreSQL 연결 시간대에서 실행해 모두 통과했다.
`verificationUsesRequestedServerAndDatabaseTimezones`는 JVM 기본 시간대와
PostgreSQL `SHOW TIME ZONE`이 지정값인지 확인한다.

- `ProgramScheduleBoundaryIntegrationTests`: 32개
- `ProgramScheduleApiIntegrationTests`: 10개
- `ProgramScheduleMigrationTests`: 1개
- `ProgramInstantEnforcementTests`: 4개
- `ProgramStatusSchedulerTests`: 4개
- `ProgramStatusTransitionTests`: 2개
- `ParticipantAttachmentServiceTest`: 22개

프론트는 UTC에서 전체 24개, 미국 서부와 서울에서 기간 관련 15개씩 통과했다.
시간대 변경은 Node 프로세스의 `TZ`와 JVM 테스트 프로세스/DB 연결 설정에만 적용했으며,
사용자 PC의 시스템 시간대는 변경하지 않았다. 브라우저 자체의 시간대 변경 검사는 수행하지 않았다.

백엔드 결과: `backend/build/reports/tests/schedule-{UTC,America-Los_Angeles,Asia-Seoul}/index.html`.
실행용 임시 Gradle init script는 `backend/build/schedule-verification.init.gradle`에 있다.

```powershell
# backend 디렉터리에서 실행; timezone 값만 바꿔 세 번 실행
.\gradlew.bat --init-script build/schedule-verification.init.gradle '-Dverification.timezone=UTC' test --tests '*ProgramSchedule*' --tests '*ProgramInstantEnforcementTests' --tests '*ProgramStatus*' --tests '*ParticipantAttachmentServiceTest' --max-workers=2 --console=plain

# frontend 디렉터리에서 실행
$env:TZ='UTC'
node --test tests/*.test.mjs
$env:TZ='America/Los_Angeles'
node --test tests/programSchedule.test.mjs tests/evaluationPeriod.test.mjs
$env:TZ='Asia/Seoul'
node --test tests/programSchedule.test.mjs tests/evaluationPeriod.test.mjs
```

## 브라우저 재현

실제 React 페이지에 임시 API 응답을 연결해 검사했다. 인증된 실서버 API를 통한
전체 사용자 흐름 검사는 아니다. 브라우저 검증용 페이지는 완료 후 삭제했다.
서버 서비스 검사는 PostgreSQL을 사용하는 위 통합 테스트로 별도 수행했다.

평가 화면을 열어 둔 채 8초 뒤 평가를 시작하게 하고, 입력이 자동으로 활성화되는 것을 확인했다.
8점을 입력한 뒤 2초 뒤 마감하게 하면 입력이 비활성화되고 대기 중인 3초 자동저장은
취소됐다. 요청 수 0과 입력값 8 유지도 확인했다. 표시 갱신은 1초 간격이며 서버 검사는
요청 처리 시점의 정확한 Instant를 사용한다.

지원서 작성 화면에서는 서버 기준 마감 후에도 임시저장·지원서 제출·PDF 업로드 버튼이
활성화된 채 남았다. 제출 지원서 화면에서는 평가 시작이 10분 남아 서버 취소 가능 상태가
true인데도 취소 버튼이 비활성화됐다. 실제 요청은 서버에서 각각 기간 정책에 따라 처리한다.

### 발견한 미완료 부분

1. `frontend/src/pages/ApplicantFormPage.jsx`: `applicationDeadline` 날짜와 UTC 날짜 문자열 비교.
   시작 시각 검사와 마감 시각 자동 잠금이 없다.
2. `frontend/src/pages/ApplicantTeamPage.jsx`: 같은 날짜 기반 비교로 팀 정보 수정 버튼을 제어.
3. `frontend/src/pages/ApplicantSubmittedPage.jsx`: 마감·평가 시작을 날짜로 비교하므로
   지원서 수정이 마감 후에도 열리고, 취소가 평가 시작 당일 일찍 잠긴다.
4. `frontend/src/pages/ApplicantHomePage.jsx`, `ApplicantSubmissionsPage.jsx`: 기간 표시·D-day·목록이
   기존 날짜 기반으로 남아 있다. 정확한 시각 표시와 열린 화면 갱신 적용이 필요하다.

따라서 지원자 화면도 `schedule`의 정확한 시각과 서버 기준 시계로 전환한 후
동일한 UI 검증을 다시 해야 여섯 항목 모두 통과로 처리할 수 있다.

재현 화면: `backend/build/evaluator-boundary-verification.png`,
`backend/build/applicant-deadline-verification.png`, `backend/build/applicant-cancel-verification.png`.
